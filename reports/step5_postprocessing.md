# Пункт 5: постобработка, подписи и метаданные кадра

**Дата:** 6 ноября 2026
**Статус:** план на будущую реализацию, код ещё не менялся.

Документ фиксирует текущую постобработку, замеры, принятые решения и
предлагаемую архитектуру. Он дополняет `PLAN.md` (п. 5) и
`reports/performance.md`; геометрия жидкости и мениска остаётся в
`injector3d/liquid.py`.

## 1. Что сейчас делает постобработка

В `injector3d/render.py:_render_one()` после каждого кадра вызывается
`_postprocess()`, которая запускает отдельный процесс
`python3 postprocess_reference.py` на один кадр. Дисторсия Lensdist
применяется раньше, в композиторе Blender (`_configure_compositor`).

`postprocess_reference.py` выполняет:

1. Открывает raw PNG, конвертирует в RGBA, копирует RGB и alpha.
2. Строит маску заливки: `alpha == 0` плюс чёрные связные области,
   касающиеся границы кадра (`_border_black`, `scipy.ndimage.label`).
3. Заливает маску белым `(255,255,255)`.
4. Переводит изображение в RGB и находит самый крупный не-белый объект
   (трубку).
5. Считает высоту трубки по bbox.
6. При `--height > 0` масштабирует изображение по вертикали. В основной
   серии `SCENE_POSTPROCESS['target_height_px'] = 0`, поэтому шаг
   пропускается.
7. Создаёт белый холст `1200 + shift × 1200`, вставляет кадр со сдвигом
   `+105 px` и обрезает до `1200×1200`.
8. Сохраняет итоговый PNG.
9. Печатает диагностику: повторно ищет не-белую маску, largest component,
   bbox и ширины строк. На изображение это не влияет.

Текущая схема теряет alpha на шаге 4 и определяет трубку по «не-белому».
Поэтому она не подходит для режима «заливка выключена»: при прозрачном
фоне bbox трубки нужно считать по alpha, а не по цвету.

## 2. Замеры текущей постобработки

Условия: реальный RGBA raw 1200×1200, `shift=105`, `height=0`, медиана
3 прогонов, Blender 5.2.3. Полный вызов — **~0.57 с/кадр**, что совпадает
с `reports/performance.md` (0.56–0.57 с).

| Операция | Время | Доля |
|---|---:|---:|
| Запуск Python + импорт PIL/numpy/scipy + CLI | ~235 мс | 41% |
| Открытие и конвертация PNG | 37 мс | 6.5% |
| Маска заливки (alpha + `_border_black`) | 58 мс | 10% |
| Заливка белым | 27 мс | 4.7% |
| RGB-конвертация + largest component | 50 мс | 8.7% |
| Bbox высоты | 0.2 мс | ~0% |
| Масштабирование | 0 мс | 0% |
| Холст + paste + crop | 3 мс | 0.5% |
| Сохранение PNG (default compression) | 113 мс | 20% |
| Финальная диагностика | 50 мс | 8.7% |
| **Итого** | **~573 мс** | 100% |

Дополнительно:

- при включённом масштабе до высоты 1124 px resize добавляет ~20 мс;
- `alpha == 0` на проверенном raw даёт 1.11 млн пикселей; чёрных
  непрозрачных всего ~1.9 тыс., и они не на границе. То есть при
  `film_transparent=True` для заливки достаточно alpha, а
  `_border_black` в горячем пути, вероятно, не нужен;
- только проверка alpha занимает ~1.3 мс вместо ~58 мс у
  `_border_black`;
- сохранение PNG с `compress_level=1` — ~77 мс, с `compress_level=3` —
  ~91 мс; default level 6 даёт ~113–169 мс.

## 3. Принятые решения

- Заливка фона белым должна быть **опциональной**.
- По умолчанию заливка **выключена**.
- Цвет заливки задаётся в конфиге и может переопределяться параметром.
- Постобработку можно **полностью отключить** в конфиге и параметром
  запуска.
- Объём жидкости добавляется в имя файла между ракурсом/тегом и
  timestamp: `v<целое>` в мм³, например
  `4.6_az338_a30_n16_v12900_20261106_152208.png`.
- Объём, азимут и угол наклона могут выводиться в левом верхнем углу
  кадра; для каждого поля отдельный флаг, по умолчанию всё выключено.
- Угол наклона — **θ от вертикали**, не поворот вокруг Z.
- 3D-эллипс вычисляется аналитически по уже известной геометрии среза.
- Для задачи достаточно **центра** эллипса; координаты концов большой и
  малой осей не нужны и в метаданные не входят.
- Для 2D достаточно спроецировать **центр** эллипса; проецировать много
  точек эллипса не требуется.
- Красный маркер 3×3 px в 2D-центре — отдельная опция, по умолчанию
  выключена.

## 4. Как сейчас устроен эллипс среза

Сейчас большая/малая полуоси и координаты их концов **не используются**
как параметры построения. Эллипс возникает неявно из пересечения
цилиндрической полости с горизонтальной плоскостью.

В `_build_meniscus_bmesh()` (`injector3d/liquid.py`):

1. `rise = meniscus_wall_rise_mm()` — подъём мениска у стенки (~3.035 мм).
2. `contact_mm = level_mm + rise` — высота кромки контакта жидкости со
   стенкой.
3. `_build_flat_bmesh(mw, contact_mm, segments)` строит цилиндр радиусом
   `r_eq = _equal_area_radius(INNER_RADIUS - CLEARANCE, 192)`,
   применяет матрицу трубки `mw` и режет его плоскостью
   `plane_co=(0,0,contact_m)`, `plane_no=(0,0,1)`.
4. Верхняя крышка среза даёт граничные вершины; это и есть эллиптическая
   кромка, фактически 192-угольник.
5. Центр считается как пересечение оси трубки с плоскостью контакта:
   ```python
   center_local_z = (contact_m - mw[2][3]) / mw[2][2]
   center = mw @ Vector((0.0, 0.0, center_local_z))
   ```
6. Вершины кромки сортируются по углу вокруг `(cx, cy)`, затем по
   расстояниям до центра строятся радиальные кольца мениска.

То есть текущие параметры — это `mw`, `level_mm`, `rise`, `segments`,
`INNER_RADIUS - CLEARANCE` и `CLEARANCE`. Отдельных `major_axis` /
`minor_axis` / `ellipse_center` в коде нет.

### 4.1. Аналитический центр для будущих подписей

Для среза на высоте `h_contact` достаточно центра:

- ось трубки:
  `a = (sinθ·cosφ, sinθ·sinφ, cosθ)`;
- центр эллипса:
  `C = pivot + ((h_contact - pivot_z) / a_z) · a`, где
  `pivot = (0, 0, TILT_PIVOT_Z_MM)`.

Этого достаточно для 2D-маркера и подписи. Полуоси и их концы не
вычисляются и не сохраняются. Если позже понадобится сам эллипс, его
параметры можно получить из `R = r_eq`, `b = R`,
`A = R / |a_z| = R / cosθ` и направлений `u = normalize(a × e_z)`,
`v = normalize(e_z × u)`, но в текущей задаче они не нужны.

Важно: это эллипс **кромки контакта** на высоте `level + rise`, а не
плоскость на высоте `level` на оси. Если в подписи нужна «верхняя
плоскость жидкости» на уровне `level`, это будет другой, меньший эллипс
внутри мениска.

## 5. Предлагаемая конфигурация

Имена предварительные; важно, что у каждого вывода свой флаг.

```python
POSTPROCESS = {
    'enabled': True,
    'fill_background': False,
    'fill_color': (1.0, 1.0, 1.0, 1.0),
    'shift_x_px': 105,
    'target_height_px': 0,
}

OVERLAY = {
    'enabled': False,
    'volume': False,
    'azimuth': False,
    'tilt_deg': False,
    'ellipse_axes': False,
    'ellipse_center': False,
    'center_marker': False,
    'font_size_px': 18,
    'margin_px': 12,
    'text_color': (0, 0, 0, 255),
    'marker_color': (255, 0, 0, 255),
    'marker_size_px': 3,
}
```

CLI:

```text
--no-postprocess
--fill-background / --no-fill-background
--fill-color R,G,B[,A]
--overlay-volume / --no-overlay-volume
--overlay-azimuth / --no-overlay-azimuth
--overlay-tilt / --no-overlay-tilt
--overlay-ellipse / --no-overlay-ellipse
--overlay-center / --no-overlay-center
--center-marker / --no-center-marker
```

Поведение:

- `POSTPROCESS['enabled'] = False` или `--no-postprocess` — raw PNG сразу
  считается финальным; заливка, сдвиг, масштаб и подписи не выполняются.
  Если при этом включены overlay-флаги, вывести предупреждение.
- `fill_background=False` — фон не трогается, итоговый PNG остаётся RGBA.
- `fill_background=True` — фон композитится цветом `fill_color`;
  при непрозрачном цвете итог можно сохранять как RGB.
- overlay-флаги работают только при включённой постобработке.
- По умолчанию все overlay-флаги выключены.

## 6. Метаданные и имя файла

Постобработка не должна угадывать объём и азимут. Рендер-цикл передаёт
на кадр словарь метаданных:

```python
{
    'step': '4.6',
    'variant': 'az338',
    'azimuth_deg': 338.0,
    'tilt_deg': 30.0,
    'n': 16,
    'volume_mm3': 12900.56,
    'level_mm': 45.672,
    'ellipse': {
        'center_3d_mm': (x, y, z),
        'center_2d_px': (x, y),  # после Lensdist и постобработки
    },
}
```

Имя файла:

```text
<step>_<variant>_a<angle>_n<n>_v<round(volume_mm3)>_<timestamp>.png
```

Пример:

```text
4.6_az338_a30_n16_v12900_20261106_152208.png
```

Объём берётся из фактического меша (`info['volume_mm3']`), а не из
целевого значения. Для `render_ring()` нужны два объёма: upright и
tilted; для `render_tube()` — объём, возвращённый `on_tilt()`.

## 7. 2D-проекция и дисторсия

`bpy_extras.object_utils.world_to_camera_view(scene, camera, point)`
даёт координаты **до** Lensdist. Для маркера на финальном PNG нужно:

1. спроецировать 3D-центр через камеру;
2. применить ту же модель Lensdist, что в композиторе;
3. применить `shift_x_px` и масштаб `target_height_px` из постобработки;
4. округлить до пикселя и нарисовать маркер 3×3 px.

Для центра эллипса достаточно одной точки. Полный 2D-эллипс не нужен.
Если позже понадобится рисовать сам эллипс, точки 3D-кромки надо
проецировать и применять дисторсию к каждой; перспективная проекция
эллипса не обязана оставаться эллипсом.

## 8. Оптимизация

Приоритеты:

1. **Один процесс постобработки на серию**, а не на кадр: минус
   ~0.2–0.25 с/кадр на запуск и импорт.
2. **Асинхронная обработка предыдущего raw во время рендера следующего
   кадра**: CPU и GPU почти не конфликтуют; 0.5 с скрываются за
   ~10 с рендера.
3. **Alpha-only вместо `_border_black` и scipy в горячем пути**: минус
   ~58 мс маски; при `height=0` не искать largest component и bbox —
   ещё ~50 мс.
4. **Не выполнять resize/диагностику без необходимости**.
5. **PNG compression level 1–3** вместо default 6: минус 40–90 мс.
6. **Композитор Blender для заливки/сдвига/масштаба**, если overlay
   выключен: Python вообще не нужен, минус ~0.57 с/кадр.
7. **Overlay в batched-Python**: шрифт и метаданные загружаются один раз;
   текст/маркер стоят единицы–десятки мс.

Ожидаемый результат без переноса в композитор: **~0.10–0.15 с/кадр**
вместо 0.57 с, плюс перекрытие с рендером.

## 10. Открытые детали

- «Верхняя плоскость жидкости»: использовать кромку контакта
  `level + rise` или плоскость на уровне `level`? По умолчанию —
  кромка контакта, как фактическая граница жидкости.
- Нужен ли объём в имени и для upright-кадра, или только для наклонных?
  По умолчанию — для всех.
- Нужен ли фон под текстом в левом верхнем углу? На белом фоне
  предлагается чёрный текст с белой обводкой.
- Нужен ли `v<volume>` в имени при `POSTPROCESS['enabled'] = False`?
  Да, имя формируется до постобработки.
