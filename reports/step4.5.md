# Отчёт-план по пункту 4.5: N+1 ракурсов по окружности и оптимизация жидкости

**Дата:** 5 ноября 2026
**Статус:** 📝 Запланирован. Код ещё не менялся; это документ для реализации.

## Цель

Промежуточный пункт **4.5** между материалами (п. 4) и детальной
проработкой кадров (п. 5):

- вместо фиксированных 5 ракурсов (`upright` + 4 наклона) рендерить
  **N+1** кадров;
- трубка при фиксированном угле `θ` от вертикали описывает верхней частью
  окружность в N азимутальных положениях;
- один кадр — вертикальный, N кадров — наклон на один и тот же угол `θ`
  в разные стороны;
- N задаётся параметром запуска и/или в `config.py`;
- оптимизировать построение жидкости и мениска, чтобы N кадров не
  приводили к N полным пересчётам жидкости.

Пункт 4.5 не заменяет пункт 5: после него п. 5 занимается светом,
материалами и деталями кадров уже на новой серии.

## 1. Геометрия серии

### 1.1. Параметры

- `N` — число наклонных положений, не считая вертикали.
- Всего кадров: **N + 1**.
- `θ` — фиксированный угол наклона от вертикали (`+Z`).
- `φ_k` — азимут k-го наклона:
  ```text
  φ_k = (φ_start + k * 360° / N) mod 360°,  k = 0..N-1
  ```
- Верхняя точка трубки описывает окружность радиусом `L·sin(θ)`,
  где `L` — длина трубки.

Пример `N=4`, `θ=10°`:

| Кадр | Азимут | Плоскость |
|---|---:|---|
| вертикально | — | — |
| 1 | 270° | −YZ |
| 2 | 180° | −XZ |
| 3 | 90° | +YZ |
| 4 | 0° | +XZ |

Для `N=8` добавляются промежуточные азимуты: 225°, 135°, 45°, 315° —
всего 9 кадров.

Порядок и начальный азимут можно зафиксировать как в примере. Если нужен
канонический обход против часовой стрелки, поменять только `φ_start` и
знак шага; геометрия от этого не меняется.

### 1.2. Параметры конфигурации и CLI

Предлагаемые имена:

```python
# injector3d/config.py
TILT_AZIMUTH_COUNT = 4      # N
TILT_ANGLE_DEG = 10.0       # θ
```

CLI:

```bash
$BL --background --python injector3d/create_scene.py -- \
    4.5 --tilt-count 8 --tilt-angle 10
```

Приоритет: **CLI переопределяет config**.

Валидация:

- `N` — целое, `N >= 1`;
- `0 < θ < 90°`;
- `N=0` не допускается;
- при `θ=0` все наклонные кадры совпадут с вертикальным — либо запретить,
  либо явно предупредить.

### 1.3. Нумерация и имена файлов

Везде, где используется номер пункта плана, применять `4.5`:

- каталог: `output/4.5/`;
- PNG: `output/4.5/4.5_<ракурс>_<timestamp>.png`;
- `.blend`: `output/4.5/4.5_<ракурс>_<timestamp>.blend`
  (по-прежнему игнорируется git);
- отчёт: `reports/step4.5.md`;
- коммит: `Пункт 4.5: ...`.

Имена ракурсов:

```text
upright
az270
az225
az180
...
```

Для трассируемости лучше добавить угол и N, например:

```text
4.5_az270_a10_<timestamp>.png
4.5_upright_a10_<timestamp>.png
```

Если угол и N не в имени, их нужно писать в manifest серии.

### 1.4. Важное ограничение текущего `parse_step`

Сейчас `create_scene.parse_step()` принимает только целое:

```python
if tail and tail[0].strip().isdigit():
    return tail[0].strip()
```

`4.5` не пройдёт эту проверку и будет заменён на `1`. При реализации 4.5
нужно:

- принимать десятичный номер (`4.5`);
- в стадийной логике заменить `int(step)` на безопасное сравнение
  (`float`, кортеж `(4, 5)` или явная таблица стадий);
- проверить, что `4.5 >= 4` включает материалы и жидкость.

## 2. Что уже есть в текущей реализации

- `injector3d/render.py:112` — цикл по `TILT_VARIANTS` в одном процессе.
- Для каждого наклона:
  1. поворот трубки;
  2. `build_liquid()` — пересчёт уровня и меша жидкости;
  3. `save_as_mainfile()` (`render.py:135`);
  4. Cycles-рендер;
  5. внешняя постобработка.
- Blender **не перезапускается** и сцена **не пересоздаётся** для каждого
  кадра. Сохранённые `.blend` не используются для рендера — это побочный
  артефакт.
- Камера жёстко привязана к трубке (`scene.attach_camera_to_tube`),
  поэтому кадр не зависит от наклона, а свет остаётся в мировых
  координатах.
- Жидкость не привязана к трубке: иначе уровень наклонялся бы вместе с
  ней. Меш строится в мировых координатах и пересобирается вручную через
  callback `on_tilt`.

## 3. Замеры текущего кода

Профилировка на Blender 5.2.3 без рендера, 50 % заполнения:

| Этап | Время |
|---|---:|
| Настройка сцены и объектов | 0.14 с |
| `build_liquid()` для 5 наклонов | 8.14 с |
| Один `build_liquid()` при 30° | ~1.55 с |
| Один `build_liquid()` вертикально | ~1.91 с |
| Сохранение одного `.blend` | 0.018 с |
| Рендер 5 кадров @ 128 spp | ~65–70 с |

Внутри одного `build_liquid()` при 30°:

| Этап | Время | Доля |
|---|---:|---:|
| Всё построение | 1.546 с | 100 % |
| Плоское тело до эллиптической кромки | 0.080 с | ~5 % |
| Меш мениска | 1.419 с | ~92 % |
| Прочее | 0.047 с | ~3 % |

На наклон приходится 20–21 полная пересборка меша — это итерации
бисекции. В одной итерации:

- плоское тело: ~0.004 с;
- менисковая крышка: ~0.071 с.

На все 5 наклонов: около 7.45 с — построение мениска, около 0.40 с —
плоское тело. Профиль Юнга-Лапласа уже кэшируется; дорого не решение ОДУ,
а создание 80 радиальных колец × 192 вершины кромки, пересчёт нормалей
и объёма на каждой итерации.

Вывод: в одиночном прогоне доминирует Cycles, но при детальной проработке
и повторных рендерах 8 секунд на жидкость и N полных пересборок — уже
заметная и устранимая работа.

## 4. Автоматически ли обновляются жидкость и мениск

Нет.

- Blender не знает, что это жидкость: это статический меш.
- Мениск — результат отдельного солвера, а не модификатор и не симуляция.
- Профиль мениска зависит от радиуса, угла смачивания и свойств жидкости,
  но не от наклона; он кэшируется в `liquid._MENISCUS_CACHE`.
- При наклоне меняются уровень, эллиптическая кромка контакта и форма
  меша, поэтому `build_liquid()` обязателен, если меш не запечён заранее.
- Если жидкость привязать к трубке, она наклонится вместе с ней — это
  неверно. Если оставить в мире и не пересобирать — получится старый меш.

Handler/driver может вызывать пересчёт автоматически, но это всё равно
тот же ручной солвер. Fluid-симуляция или Geometry Nodes здесь избыточны
и вряд ли дадут нужный детерминированный мениск.

## 5. Оптимизация A: один master вместо `.blend` на кадр

- Убрать `save_as_mainfile()` из цикла по ракурсам.
- Сохранять один `master.blend` до/после серии.
- При необходимости оставить флаг `--save-variants` для отладки.

Экономия времени небольшая (~0.02 с на файл), но исчезает мусор и
неоднозначность: какие `.blend` являются актуальными.

## 6. Оптимизация B: шаблон мениска на угол

### 6.1. Идея

Для каждого угла `θ` один раз посчитать **шаблон менисковой крышки**:

- относительные координаты эллиптической кромки;
- кольца мениска относительно центра эллипса;
- смещения по `z` относительно уровня жидкости;
- топологию/индексы граней;
- объёмную поправку `ΔV_under`;
- допустимый диапазон уровней, где шаблон валиден.

При другом уровне (другом целевом объёме) шаблон не пересчитывается:
меняется только положение эллипса и объём основного тела.

### 6.2. Проверка постоянства формы

Для наклонной цилиндрической полости форма горизонтального сечения не
зависит от уровня. Проверено на уровнях 35–45 мм:

- относительные координаты кромки совпадают с точностью ~5·10⁻⁶ мм;
- число вершин кромки — 192;
- меняется только центр эллипса: при 30° он смещается примерно на
  1.73 мм при изменении уровня на 3 мм.

### 6.3. Формула объёма

Обозначения:

- `h` — уровень жидкости на оси;
- `rise = meniscus_wall_rise_mm()` — подъём у стенки;
- `h_c = h + rise` — уровень кромки контакта;
- `V_flat(h_c)` — объём плоского тела до кромки контакта;
- `ΔV_under` — объём между плоскостью кромки и мениском.

Тогда:

```text
V_meniscus(h) = V_flat(h_c) - ΔV_under
```

Важно: мениск **вычитается** из плоского тела, построенного до кромки
контакта, потому что в центре поверхность ниже кромки. Если определять
базу на уровне `h`, знак и слагаемые будут другими; проще работать через
`h_c`.

Для 30° замерено:

- `ΔV_under ≈ 668.20 мм³`;
- при уровнях 38, 40, 42, 45 мм поправка постоянна в пределах ~0.001 мм³.

### 6.4. Как использовать

1. Один раз на угол `θ` построить шаблон крышки и измерить `ΔV_under`.
2. При бисекции уровня считать только дешёвое плоское тело:
   `V(h) ≈ V_flat(h + rise) - ΔV_under`.
3. На финальном уровне один раз собрать полный меш: плоское тело +
   закэшированная крышка, перенесённая в центр эллипса.
4. При смене уровня/заполнения крышку не пересчитывать.
5. При смене `θ` использовать другой шаблон.

Ожидаемо: с ~1.55 с до ~0.10–0.20 с на наклон, то есть в 8–10 раз
быстрее. На 5 наклонов вместо ~8.1 с — порядка ~1 с плюс одноразовый
прогрев шаблонов ~0.4 с.

### 6.5. Ограничения шаблона

- Валиден, пока плоскость контакта пересекает полную цилиндрическую
  стенку. У дна и у перелива текущий код использует плоский fallback —
  сохранить эту логику.
- При изменении уровня центр эллипса смещается; крышку надо переносить
  по `x/y/z`, а не просто переиспользовать.
- Кэш зависит от `θ`, радиуса, `CLEARANCE`, `REVOLVE_SEGMENTS`,
  `MENISCUS_RINGS`, угла смачивания и свойств жидкости.
- Сейчас меш жидкости игнорирует внутренние галтели трубки. Если позже
  моделировать жидкость по галтели, постоянство эллипса нарушится.
- Нужно сравнить старый и новый расчёт объёма на нескольких уровнях и
  прогнать `check_liquid.py`.

## 7. Оптимизация C: риг азимута и один наклонный меш

Для серии N+1 не нужно строить жидкость N раз. При фиксированном `θ`
все наклонные положения — это один и тот же меш, повёрнутый вокруг Z.

Предлагаемый риг:

- пустышка `AzimuthRig` в начале координат;
- `AzimuthRig.rotation_euler.z = φ`;
- трубка — дочерняя `AzimuthRig`, локальный наклон `R_y(θ)` фиксирован;
- камера — дочерняя трубке, как сейчас;
- жидкость — дочерняя `AzimuthRig`, но **не** трубке.

Тогда:

- трубка наклонена на одинаковый угол `θ`;
- при изменении `φ` связка трубка + камера + жидкость поворачивается
  вокруг Z;
- жидкость остаётся горизонтальной, потому что вращение вокруг Z её не
  наклоняет;
- камера сохраняет одинаковый кадр относительно трубки;
- свет остаётся в мировых координатах, поэтому каждый азимут даёт другое
  освещение/рефракцию.

Для вертикального кадра нужен отдельный upright-меш; для всех наклонных —
один наклонный меш на `θ`. Итого на серию: **2 построения жидкости**
(вертикаль + один наклон), а не N+1.

Нельзя делать наклон через `rotation_euler = (θ·cosφ, θ·sinφ, 0)`:
из-за некоммутативности Эйлеровых поворотов итоговый угол от вертикали
будет «плавать». Нужен риг или кватернион/осевое вращение.

## 8. Оптимизация D: master `.blend` с готовыми вариантами

Для повторных рендеров п. 5:

- собрать сцену один раз;
- сохранить `master.blend` с трубкой, камерой, светом и жидкостью;
- хранить upright-меш и один наклонный меш (или 5 готовых мешей, если
  уровни фиксированы);
- для N+1 кадров анимировать `AzimuthRig` по Z либо рендерить циклом;
- не сохранять `.blend` на каждый кадр.

Если нужны фиксированные 5 уровней, можно запечь 5 полных мешей. Но
шаблон мениска гибче: он позволяет менять уровень без пересчёта крышки.

Shape keys не использовать: топология жидкости меняется между плоским
fallback и мениском, а также может меняться число/порядок вершин кромки.
Отдельные mesh-датаблоки или объекты надёжнее.

1. **Документация и нумерация** — этот файл, `PLAN.md`, `AGENTS.md`,
   `README.md`, `KODA.md`, `CHANGELOG.md`.
2. **Параметры** — `TILT_AZIMUTH_COUNT`, `TILT_ANGLE_DEG`; CLI
   `--tilt-count`, `--tilt-angle`; поддержка `4.5` в `parse_step()`.
3. **Генератор ракурсов** — `tilt_variants(n, angle)` вместо жёсткого

4. **Риг азимута** — `AzimuthRig`, локальный наклон трубки, камера
   дочерняя, жидкость дочерняя ригу.
5. **Один наклонный меш** — vertical + один tilted, поворот вокруг Z.
6. **Шаблон мениска** — `ΔV_under`, плоский объём в бисекции, финальная
   сборка с кэшированной крышкой.
7. **Master-файл** — один `.blend`, без сохранения на каждый кадр.
8. **Проверки** — `check_liquid.py`: вертикаль + один наклонный
   представитель; объём, горизонтальность, manifold; сравнение старого
   и нового меша.
9. **Рендер 4.5** — N+1 кадров в `output/4.5/`, имена `4.5_...`.
10. **Отчёт** — обновить этот файл статусом и фактическими метриками.

## 10. Ожидаемый результат

- N+1 кадров при `N=4` → 5, при `N=8` → 9.
- Верх трубки описывает окружность, угол `θ` одинаков для всех наклонов.
- Один наклонный меш жидкости на серию, а не N.
- Построение жидкости ускоряется примерно в 8–10 раз.
- Один master `.blend` вместо N+1 файлов.
- Повторные рендеры п. 5 не тратят время на пересборку сцены и жидкости.

## 11. Риски и что не делать

- Не полагаться на автоматическое обновление жидкости в Blender.
- Не привязывать жидкость к трубке — уровень наклонится.
- Не строить полный `build_liquid()` N раз для N азимутов.
- Не использовать shape keys для вариантов жидкости.
- Не задавать наклон суммой Эйлеровых X/Y.
- Не считать, что `.blend` на каждый кадр нужен рендеру.
- Не забыть fallback у дна/перелива.
- Не забыть инвалидацию кэша при изменении геометрии/параметров.

## 12. Критерии приёмки

- `N=4`, `θ=10°` даёт ровно 5 кадров; `N=8` — 9.
- Все наклонные кадры имеют одинаковый угол от вертикали.
- Вертикальный кадр и N азимутальных не перезаписывают друг друга.
- Объём жидкости одинаков для всех кадров в пределах допуска.
- Верхняя кромка горизонтальна, меш manifold.
- `check_liquid.py` проходит.
- В `output/4.5/` лежат PNG `4.5_...`; `.blend` не отслеживается git.
- Нет N полных пересборок жидкости; в идеале — 2 на серию.
